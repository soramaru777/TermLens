# TermLens の課題と次の優先順位

## 次の優先順位

2. ~~**セッション復元**（弱点4の残り）~~ — Issue #9 後半として実装済み(下記)。iOS のタブ破棄からの
   復元は実機未検証

## A. 未検証

1. **話者分離の実効精度（複数話者）** — iPad 実機で話者チップ（話者A）の表示までは確認したが、
   **話者は 1 人のみで分離精度は未検証**。合成音声では全発言が話者0に落ちるため実声が必要
   （[[termlens-stt-pipeline]]）

> 2026-08-25 追記: **テスト基盤（Issue #18）を入れたが、上記1は解決していない。**
> 何が測れるようになり、何が依然として測れないかを [[termlens-testing]] に整理した。要約:
>
> - **測れるようになった** — 話者分割ロジック（Issue #20 以降は `splitBySpeaker()`。
>   それまでは `dominantSpeaker()` の多数決）、`normalizeTerm()` の表記ゆれ吸収、エラー分類
>   （恒久／一時）と利用者向け文言、`stripInlineCitations()` の除去範囲、ローパス FIR の
>   振幅応答（通過域・阻止域・直流ゲイン・線形位相）。ここは CI が毎回回す
> - **測れるようになった（オプトイン）** — 用語抽出そのものの精度。合成ケース（#24 時点で17件）で
>   Recall / 正しい補正率 / 誤補正率 / probable 率 / unresolved 率 / カード Precision を出す。
>   `RUN_LLM_EVAL=1` のときだけ動く（実 API 課金と非決定性を CI に持ち込まないため）
> - **依然として測れない① CER / WER** — 文字誤り率・単語誤り率を出すには正解トランスクリプト
>   付きの実音声が要る。そういう資産が無いので、文字起こしの品質は今も定量化できていない
> - **依然として測れない② Deepgram 自身の話者クラスタリング精度** — テストが押さえているのは
>   「単語配列 → 話者番号」の変換だけで、各単語に `speaker` を付けているのは Deepgram。
>   複数話者の実声でしか検証できない。**未検証1はここに残る**
> - **依然として測れない③ AudioWorklet の実機挙動** — FIR の係数は検証できるが、
>   worklet が実際に動くか、`lowpass.js` の static import が iPad Safari で通るかは実機のみ

> 2026-08-26 追記: **Issue #20 で話者分割を多数決から word 単位に変えたが、未検証1はさらに
> 重くなった。** 多数決は Deepgram の `speaker` の揺れを吸収していて、それが精度の低さを
> 見えにくくしていた。閾値を入れずに素直に分割した今、**揺れは細切れの発話としてそのまま
> 画面に出る**（`[0,1,0,1]` なら 4 発話）。どの程度細切れになるかは複数話者の実声でしか
> 測れないため、実機確認（Pixel 9a）と評価基盤での話者誤分類率の比較が必要な状態のまま。
> 閾値を入れるかどうかはその測定結果を見てから判断する（[[termlens-stt-pipeline]]）。

> 2026-08-29 追記（Issue #36）: **細切れの実測が取れ、表示側の補正を入れた。** Android 実機の
> 約 49 分・複数話者セッションで、補正なしの `groupUtterances()` は 642 グループを作り、うち
> 3 文字以下が 255 件（約 39.7%）。その約 78% が同一秒内に複数 speaker が切り替わる箇所に
> 含まれていた。`splitBySpeaker()` は変えず、`public/utterances.js` が表示・エクスポート用の
> コピーの上で `speaker` ラベルだけを補正する（**テキストは 1 文字も消さない**。
> [[termlens-stt-pipeline]]）。
>
> **未検証1（Deepgram 自身のクラスタリング精度）はそのまま残る。** 補正は「揺れが表示に露出する」
> ことへの対処であって、話者の割り当てが正しいかは何も測れていない。加えて **#36 で 2 つ増えた**:
>
> - **閾値の妥当性が未検証** — `JITTER_CHAR_LIMIT` = 4 / `JITTER_WINDOW_MS` = 500 は上記の分布から
>   置いた暫定値。実機での前後比較（同じ会議の補正あり/なしを人が読み比べる）はまだ行っていない。
>   外したときの害は「短い発話が隣の話者の段落に混ざる」ことで、発言の消失ではない
> - **本物の相槌を吸収してしまう頻度が未計測** — 別 final の相槌は `seq` の不一致で構造的に守られるが、
>   1 つの final の中に相槌ごと入っている場合は区別できない。どれくらいあるかは実声でしか測れない

> 2026-08-26 追記: **Issue #21 で発話の切れ目を Deepgram のシグナルに委ねたため、
> 未検証の範囲がさらに広がった。** `speech_final`（無音検出）と `UtteranceEnd`（word ギャップ）
> のどちらも、日本語の実会議でどれだけ届くかを一度も観測していない。届かない場合、
> 発話は 3 秒のタイムアウトで閉じられ、**切れ目が会話の内容と無関係に決まる**。
> 公式ドキュメントは背景ノイズで `speech_final` が来なくなる失敗モードを明記しており、
> 会議室の用途では例外ではなく想定内。まずログに出して届くかを確かめる必要がある。

> 2026-08-27 追記: **Issue #22 で直前の会話を抽出の文脈に渡したが、効果も副作用も未実測。**
> 狙いは語義判定の材料を増やすことだが、**文脈に引きずられた誤補正が増える**方向にも効きうる。
> 同じ fixture を `EVAL_NO_CONTEXT=1` の有無で2回回せば Recall・正しい補正率・誤補正率・
> Precision を比較できる仕組みまでは入れた（[[termlens-testing]]）が、実 API 課金が伴うため
> **まだ回していない**。あわせて入力トークンが1回あたり最大 1,100 トークンほど増えるので、
> カード表示のレイテンシが #21 の実測（最悪13秒）から悪化していないかも実機確認が要る。
>
> **AC「過去文脈の用語を再カード化しない」は CI では検出できない。** `surfaceForms` の出所は
> `filterSurfaceForms()` で決定的に担保したが、こちらを支えているのはプロンプト規則9と既存の
> `shownTerms` だけで、検出手段は課金を伴う `context-no-recard` ケースしかない。
> サーバー側で機械的に落とす案（`surfaceForms` が空のカードを捨てる等）は、
> 「クバネテス」→ `Kubernetes` のような正当な補正カードを巻き添えにするので採らなかった。

> 2026-08-27 追記: **Issue #25 で検索回数に上限を入れたが、値は暫定で根拠がまだ無い。**
> 現状で1カードあたり何回検索しているかを一度も測っていないため、`verifyAndEnrich()` の
> 戻りに `searches` を足して `VerifyTally` に集計するところまでを先に入れてある。
> **人が `MAX_WEB_SEARCHES=0 EVAL_WITH_VERIFY=1 npm run eval:llm`（＝上限を外した状態）で
> 分布を見て値を決め、入れた状態で再度回して `unresolved` 率・`unresolvedRecall` が
> 悪化していないか（＝絞りすぎていないか）を確認する**必要がある。絞りすぎは #24 の
> 最大リスク（過剰 unresolved）を悪化させる方向に効く。
>
> あわせて **`max_tool_calls` を実 API が受け付けるかも未検証**。Responses API の body
> パラメータだが、SDK 7.4.0 の stable な型定義には無い（beta 名前空間側にはある）ため
> `searchLimit()` の戻り値の型でこのキーだけを通している。もし 400 が返る場合、
> `isPermanent()` が true を返して**そのセッションの検証が丸ごと止まる**。
> 発生確率は低い（パラメータ自体は SDK の beta 側の型に実在する）が影響は全損なので、
> **コードにフォールバックを足すのではなく、確認をマージ前の1回に前倒しする**のが
> 決定的な対処になる。上の計測ランがそのまま確認を兼ねる。
>
> なお **`verifyDisabled` が立ったことは `onError` で利用者へ通知するようにした**（#25 の
> レビュー指摘）。以前は無言で、以降ずっと未検証のカードが出続けることを誰も知れなかった
> （`willEnrich` が false になるので確認中の表示すら出ず、画面からは正常時と区別がつかない）。
> `permanent` は立てない — 抽出は生きているのでカード自体は出続ける。

> 2026-08-27 追記（#25 の simplify レビューで挙がり、この Issue の範囲外として見送ったもの）:
>
> **1. 用語集のポリシーがセッション境界に無い。** 「用語集のどのエントリが機外へ出てよいか」は
> 本来セッション単位の方針だが、実装は検証段の手前のフィルタ1枚。同じ用語集は
> **STT の keyterm（`session.ts`）と抽出プロンプト（`extractor.ts`）には全件が渡っている**。
> 深く直すなら、セッション開始時に1度だけ分類した値を持たせ、各消費者にはそれぞれ許された
> 射影だけを渡す。今回は `verifyAndEnrich()` の口を絞り込み済みの `glossaryHints` にして、
> **検証経路だけは型で担保**するところまで。
>
> **2. 検証結果を判別共用体にしていない。** `chosen: string | null` と
> `rejection: RejectionKind | null` は「chosen があれば rejection は null」という不変条件を
> **コメントだけ**で結んでおり、消費者が `?? "unspecified"` を書く必要がある。実際、
> レビューで**差し替えを「理由なしの棄却」としてログする不具合**が見つかった（修正済み・
> 回帰テストあり）。`{ kind: "accepted" | "replaced" | "rejected" | "unverified" }` に
> すれば同じ間違いが型として書けなくなるが、`parseVerifyOutput()` の形を全面的に変えるので
> #23・#24 のテストごと書き直しになる。
>
> **3. 検証が完了しなかったときの降格経路が無い。** hard cap の打ち切りやパース失敗は
> `enrichCard` の catch に落ち、**速報の断定的な解説と `status` がそのまま残る**。
> `SEARCH_LIMIT_HEADROOM` はその経路に入る確率を下げているだけで、経路自体は開いている。
> ただし catch を一律に降格させると、一時的なネットワークエラーでも `unresolved` に落ちて
> **#24 の最大リスク（過剰 unresolved）を悪化させる**ので、「上限起因の打ち切り」だけを
> 区別する必要がある。その判別には `incomplete_details.reason` の実値が要るが未確認。
>

> > `willEnrich: true` の予告をしていない既存カードが対象なので、失敗しても
> > `card_update` を送らず `unresolved` のまま据え置くのが正しい（送らないと
> > 確認中が残る、という上の問題がそもそも発生しない）。上記3は通常の Stage 2 の話。

> 2026-08-27 追記: **Issue #26 の収音モードと閾値は、どちらも実機で確かめないと決まらない。**
> 実装は入れたが、人の判断待ちが3つ残っている（[[termlens-stt-pipeline]] の「マイクの取得設定」）。
>
> **1. スピーカー収音モードの constraints が妥当か。** `echoCancellation: true` は
> 「マイクがスピーカーの音を拾う二重入力を消す」という**仮説**で置いた。ブラウザの
> エコーキャンセルは**自端末の**出力を参照して打ち消す実装なので、**別の端末**の
> スピーカーを拾う場合は参照信号が無く効かない可能性がある。効かないようなら `false` に倒す。
> **既定の対面会議モードは #26 以前と同一**なので、ここが外れていても既存の使い方には影響しない。
>
> **2. 無音・クリップの水準は既定値のまま。** ただし**閾値を決める作業ではなくなった** —
> レビュー対応で分布（窓ごとの RMS の dBFS ヒストグラム）を出すようにしたので、
> `SILENCE_DBFS`（-40）は**表示時に当てる読み値**で、実機のエクスポートを見れば
> 「この端末の底は -45dBFS」と直接読める。既定値が合わなければ変えればよく、
> **合わないことも分布から分かる**（以前は無音率 100% と出るだけで底が読めなかった）。
> `CLIP_THRESHOLD`（0.99）は端末に依らない量なので暫定のままでよい。
>
> **3. Pixel 9a での2モード比較そのもの（AC5）。** 同じ音源・同じ距離で両モードを試し、
> 文字起こしの質と診断の数値を見比べる。数値で比べられるようにしたのが #26 案B の目的で、
> **その数値を読む作業はまだ誰もやっていない**。

> 2026-09-01 追記: **Issue #40（unresolved カードの再評価）の上限値・閾値は全部が暫定で、
> 1つも計測していない。** `MAX_WEB_SEARCHES` とまったく同じ状況を意図的に作ってある —
> 分布を測る手段（指標とレポート行）を先に入れ、値は人が測ってから決める。
>
> | ノブ | 既定値 | 決め方 |

> | `REMATCH_MIN_SIMILARITY` | 0.5 | **`REMATCH_MIN_SIMILARITY=0` で絞り込みを外して**分布を測ってから決める |
> | `MAX_REMATCH_ATTEMPTS` | 2 | 同上（上限を入れたまま測ると分布が壊れる） |
> | `REMATCH_COOLDOWN_MS` | 30,000 | 同上 |
> | `MAX_REMATCH_PER_RUN` | 2 | コード内の定数。上の3つを決めてから見直す |
> | `MAX_PENDING_UNRESOLVED` | 20 | 同上 |
>
> **人がやる必要があること:**
>
> 1. `REMATCH_MIN_SIMILARITY=0 RUN_LLM_EVAL=1 EVAL_WITH_VERIFY=1 npm run eval:llm` で

> 2. **`rematchMiscorrection`（再評価による誤補正率）と全体の `miscorrection` をセットで見る。**
>    unresolved 率だけが下がって誤補正が増えていたら閾値を締める。
>    unresolved 率だけを下げることを成功条件にしない
> 3. **実機で確認する** — (a) 会議中に再評価が発火するか (b) 改名がその場で反映されるか
>    (c) 誤補正が増えていないか (d) 統合が起きたときに表示が飛ばないか。
>    **合成 fixture では測れない**（[[termlens-testing]]「この仕組みで測れないもの」）
> 4. 追加 API 呼び出し数（`VerifyTally.rematchChecked`）を確認し、想定（現状の Stage 2
>    呼び出し数に対して数％〜十数％の増分）と合っているか照合する

### 候補一致の効果が未計測（#42）

> 2026-09-02 追記。実装は入れたが、**効果を1度も測っていない**。

読み注記付きの `chosen` を候補へ寄せる修正（[[termlens-term-extraction]] の
「候補一致は3段」）は、決定的テストで「別用語を通さないこと」までは固定してあるが、
**実データでの効き方は測っていない**。

**人がやる必要があること:**

1. **develop と修正後の両方で** `RUN_LLM_EVAL=1 EVAL_WITH_VERIFY=1 npm run eval:llm` を
   回し、`out-of-candidates` 件数 / `unresolved` 率 / 補正率 / **誤補正率**を比較する
2. **`out-of-candidates` が減ったこと自体を成功条件にしない。** 別用語まで通してしまえば
   その数字は下がるので、**誤補正率と必ずセットで読む**（#40 の再評価と同じ読み方）
3. 実機セッションで、読み仮名注記による不要な `unresolved` 降格が消えたことを確認する

決定的テストが押さえられるのはここまで、という線が #40 と同じ位置にある。
合成データで固定できるのは判断の形（別用語を通さない）で、**実データでの誤補正率の変化は
モデルの実行結果でしか測れない**。

> **最大リスクは再評価による誤補正の増加。** `unresolved` は #24 が意図的に安全側へ倒した
> 状態で、そこから昇格させる経路は当時わざと塞いだもの。ローカル判定が緩いと、
> 音が似ているだけの無関係な確定用語に引っ張られる。歯止めは2枚:
> 「**昇格するのは web 検証を通ったものだけ**」（`isRelated()` は検証に回す候補を絞るだけ）と、
> 「**改名を伴わない昇格は許さない**」（`isRename()`）。後者が無いと、合成候補の先頭が
> 抽出段の推定 term 自身であるために「検証段がそれを選び直すだけで格上げ」が通り、
> #24 が塞いだ形がそのまま復活する。
>
> **発火率は上限と閾値だけで決まらない。** 手がかりは `fresh` のカードなので、ある用語が
> 手がかりになるのはその run 1回きり。(a) 同じチャンクに未解決とその手がかりが揃ったペア
> (b) `MAX_REMATCH_PER_RUN` で溢れたペア は、**どちらも以後どの回でも評価されない**。
> 計測で「発火しない」と出たとき、閾値のせいなのか取りこぼしのせいなのかを
> 取り違えないこと（[[termlens-term-extraction]]「取りこぼしは2つあり、どちらも恒久的」）。
>
> **評価ハーネスの数字は本番と母集団を揃えてある。** 再評価の対象は「抽出段が unresolved に
> したカード」だけで、Stage 2 が降格させたカードは含めない（本番の `pendingUnresolved` に
> 積まれないため）。検索回数と失敗も `rematchSearches` / `rematchFailed` として
> Stage 2 の `searches` / `failed` とは別に数える — 混ぜると `MAX_WEB_SEARCHES` を決める
> ための「1カードあたり平均検索回数」が水増しされる。

> 2026-08-13 解決: **Docker ビルド**。Fly のリモートビルド（`fly deploy --remote-only`）で成功し、colima 不要になった。デプロイ完了。

> 2026-08-13 一部解決: **iPhone/iPad 実機**。iPad の Safari でマイク許可と音声からの文字起こしが
> 動作することを確認した。残るのは複数話者での分離精度（上記1）。

## B. 実装上の弱点

4. **セッション復元なし** — 状態はブラウザメモリのみで**リロードで全消失**する。自動再接続（下記）は実装済みなので、残るのはリロード/タブ復帰時の復元のみ

> 2026-08-18 一部解決: **自動再接続**（Issue #9 前半）。WS が意図せず切断しても即終端にせず、
> 指数バックオフ（1s, 2s, 4s, 8s, 16s、最大5回）で `connectWs()` を呼び直すようにした
> （`public/app.js`）。以下は実装上の判断。
>
> - **マイクは再接続中も離さない**。`releaseCapture()` / `cleanupAudio()` は呼ばず、
>   `sendAudio = false` で送信だけ止める。離してしまうと再接続できてもマイクが無く
>   音声が送れなくなるため
> - 再接続試行は `connectWs()` をそのまま再利用する。`start` メッセージと `getGlossary()` の
>   再送は既存の `open` ハンドラがそのまま行うので、再接続専用の送信コードは不要だった
> - 送信の再開は既存の `case "ready":`（`sendAudio = true`）に乗せている。再接続用に
>   別の合図を用意する必要はなかった
> - **認証失敗の分岐（`!everReady && 1006`）と、停止操作中・`finished` 後は再接続しない。**
>   当初は「1006 かつ文字起こしが空」で判定していたが、無音のまま回線が切れた場合に
>   正常な接続でも「トークンを確認してください」と誤表示する問題があったため、判定材料を
>   「`ready` を一度でも受け取ったか（`everReady`）」に変更した。`ready` はサーバーがトークンを
>   受理した後にしか返らないため、無音による誤表示を避けつつ認証失敗と回線断を確実に
>   切り分けられる。トークン誤りで5回粘るのは無意味だし、停止後にタイマーが生き残ると
>   勝手に再接続してしまうため、停止ボタンのハンドラで待機中の `setTimeout` を明示的に
>   `clearTimeout` する
> - **サーバーは再接続のたびに新しい STT セッションを張るため、Deepgram の話者番号が
>   振り直しになる。** 再接続前後で「話者A」が別人になり得ることをユーザーに示すため、
>   `finalLines` に `{ type: "reconnect" }` という区切り印を入れ、`groupUtterances()` で
>   前後の発話とグルーピングされないようにした。画面描画（区切り行）と Markdown
>   エクスポート（`---` + 注記）の両方に同じ印を反映させている
> - `resetSessionState()` にも再接続の試行回数・待機タイマーの初期化を追加した。認証失敗や
>   マイク拒否はリロードを挟まずホームに戻るため、残っていると次回セッションに持ち越す
>
> **未着手のまま残るのはリロード/タブ復帰時のセッション復元**（サーバー側にセッション状態を
> 持たせて再接続後に文字起こし・カードを復元する、など）。今回のスコープには含めていない。

> 2026-08-19 解決: **セッション復元**（Issue #9 後半）。`finalLines`・`cardData`・
> `sessionStartedAt` を `localStorage`（キー `termlens.session`）に保存し、ホーム画面起動時に
> 保存済みセッションがあれば「いつの会議か・発言数・カード数」を示す案内を出して復元できる
> ようにした（`public/app.js`, `public/index.html`, `public/style.css`）。以下は実装上の判断。
>
> - **保存対象からアクセストークンと音声を明確に除外**。トークンは別キー（`termlens.token`）で
>   既に保存されており、セッションデータに含める理由がないため
> - **保存は既定 ON**。設定画面に「会議の内容をこの端末に保存する」チェックボックス
>   （キー `termlens.persist`、未設定は ON 扱い）を追加し、既存の「保存ボタンで確定、戻るで破棄」の
>   挙動にそのまま乗せた。OFF にした瞬間、保存済みの `termlens.session` も削除する（残り続けると
>   ユーザーの意図に反して復元案内が出てしまうため）
> - **保存は 1 秒デバウンス**。文字起こしは数秒に 1 回、カード更新も走るため毎回書くと重い。
>   `addCard()` / `updateCard()` / 確定文字起こしの push 直後で一律 `scheduleSessionSave()` を
>   呼ぶだけにし、呼び出し漏れが起きにくいようにした
> - **`visibilitychange` の `hidden` を主な即時書き出し経路にした**。`beforeunload` は iOS で
>   発火が不確実なため採用しなかった
> - **保存すべき区間の判定に既存の `captureActive` を流用した**。`finalLines`/`cardData` が
>   変化しうるのはマイク/WS を保持している間（停止後の flush 待ちを含む）だけなので、専用の
>   フラグを別に持つ必要がなかった。この結果、復元表示中(閲覧のみ、`captureActive` は false)は
>   自動的に保存処理が素通りする
> - **24 時間の期限切れは読み込み時に無条件で破棄し、案内も出さない**(要件どおり)。`savedAt`
>   を保存時刻として持たせ、読み込み側でだけ経過時間を判定する
> - **容量対策として、書き込み前に JSON 文字列長が目安 2MB を超えたら古い `finalLines` から
>   1 割ずつ捨てて収める**。`cardData`(用語解説の本体)は削らない。`localStorage.setItem` 自体は
>   容量超過で例外を投げるため、書き込みは try/catch で必ず囲み、失敗しても会議は止めない
> - **「復元する」は本番画面を終端状態(停止後と同じ)で開くだけで、`connectWs()` は一切呼ばない**。
>   `ws` は null のまま、`captureActive` も false のまま。マイクも WebSocket も張らないことを
>   徹底し、「復元=持ち出し目的、続きを録る手段ではない」を守った
> - **カードは `addCard()` を素通りさせて復元する**(`case "cards":` と同じ経路)。これにより
>   `cardData` の再構築と DOM 描画が同時に済む。ただし `addHighlightTerm()` は `addCard()` の
>   内部では呼ばれないため、`case "cards":` と同様に呼び出し側(復元処理)で明示的に呼ぶ必要が
>   あった。ここを忘れると、カードは描画されるのに会話中の用語がオレンジ表示にならない
> - **セッションを正常に終えて「戻る」でホームに帰るときは `termlens.session` を削除する。**
>   会議が終わって持ち出しも済んだ内容を残し続けない。この削除は既存の「戻る」ハンドラ
>   （`finished` 分岐、未保存警告の後・`location.reload()` の直前）に 1 行足すだけで済み、
>   通常セッションでも復元後のセッションでも同じコードパスを通る
> - `cardData` は `Map` のため `JSON.stringify` できず、`[...cardData]`（`[term, card]` の配列）に
>   落として保存し、復元時は配列を舐めて `addCard()` を呼び直すことで `Map` に戻している
>
> **iOS 実機でのタブ破棄からの復元は未検証のまま残る。**(自動再接続と同様、シミュレータや
> デスクトップ Safari での検証はしていない)

> 2026-08-17 解決: **会議ログのエクスポート**（旧5）。停止後に文字起こしと用語カードを
> それぞれ Markdown でダウンロードできるようにした（`public/app.js` の
> `buildTranscriptMarkdown` / `buildTermsMarkdown`）。以下は実装上の判断。
>
> - カードの元データは DOM にしか無かったため、`cardData`（term → TermCard の Map）を追加した。
>   DOM は新しい順に prepend するが Map は挿入順を保つので、エクスポートは登場順になる
> - `finalLines` に受信時刻を持たせ、会議開始からの経過時間を出す。**発話時刻ではなく
>   サーバーが確定結果を返した時刻**なので、実際の発話より遅れる
> - ホーム画面に追加した PWA では `<a download>` が働かない場合があるため、スタンドアロン
>   表示かつ `navigator.canShare({files})` が真なら共有シートを優先する。**iPad 実機では未検証**
> - 「戻る」はリロードで内容を破棄するため、未保存なら1回目のタップで警告する。
>   確認ダイアログは PWA で挙動が不安定なため使っていない。未保存の判定は
>   **文字起こしと用語カードで別々**に持つ（片方だけ保存して戻ると、もう片方が失われるため）
> - **セッションの終端は必ず `finish()` を通す**。停止操作・意図しない切断・認証失敗の
>   いずれも `releaseCapture()` でマイク・AudioContext・Wake Lock を解放する。
>   解放を怠るとページをリロードするまでマイクが掴まれたままになる
> - **停止ボタンのハンドラは1本に保つ**。`addEventListener` と `onclick` を併用すると
>   「戻る」を押すたびに停止処理まで走り、`finish()` の再実行で警告状態がリセットされて
>   永久に戻れなくなる。`finished` フラグで分岐する
> - **開始のたびに `resetSessionState()` を通す。** 認証失敗とマイク拒否はリロードを挟まず
>   ホームに戻るため、前回の終端状態（`finished` など）が残る。残ると次のセッションで
>   停止ボタンが「戻る」のままになり、停止できなくなる
> - **1006 の認証失敗判定は `!stopping && !finished` で囲う。** 停止処理中の切断を
>   認証失敗と誤判定すると、「トークンを確認してください」と嘘を表示したうえ、
>   終端状態を抱えたままホームに戻る
> - **解放処理はグローバルを `await` の前に外す**（`releaseCapture` / `cleanupAudio`）。
>   `await` のあとで `null` を代入すると、その間に開始し直した新しいセッションの
>   `AudioContext` や `ws` を消してしまう
> - **`finished` は解放が済んでから立てる。** 先に立てるとボタンが「停止」の見た目のまま
>   戻る側の分岐に入り、破棄警告が表示されないまま消費される
> - **`acquireWakeLock()` は `await` されない。** 取得中にセッションが終わっていたら
>   その場で解放する。しないと誰も解放しないロックが残り、画面が点いたままになる
> - **`<a download>` の成否は取れない。** スタンドアロン表示では「保存できた」と見なさず、
>   未保存警告を残す側に倒す

> 2026-08-17 追加: **狭い画面でのカード1枚表示**。縦積みレイアウト（`max-width: 899px`）では
> カードを最新1枚だけ表示し、会話中の用語タップでその語に固定、「最新」ボタンで追従へ戻す。
> 表示切り替えは CSS（`.card.active` 以外を `display:none`）で行い、JS は `.active` の
> 付け替えだけを担う。そのため画面回転で追加の処理が要らない。
>
> **閾値 899px は既存の横並び切り替えと共用**しており、`public/app.js` の `stackedLayout`
> と `public/style.css` のメディアクエリが対になっている。片方だけ変えると壊れる。
> **iPad の縦向きもこの閾値に入る**ため 1 枚表示になる。分けたい場合は両方の閾値を下げる。
6. **Deepgram の final が文の途中で切れる** — 抽出チャンクが分断される。`endpointing` 調整の余地あり（[[termlens-stt-pipeline]]）
7. **清書選定が一発勝負** — レア度上位の半数に漏れた用語は以後も検索されない。また前置き除去が「最終段落を採用」のヒューリスティックのため、まれに本文前半を落とすリスクがある（[[termlens-term-extraction]]）
8. **長時間会議でフロント全再描画** — 数百発言を超えると性能劣化の可能性
12. **恒久エラーを一時エラーと区別せず再試行し続ける** — `src/extract/scheduler.ts:110-125`。
    失敗したチャンクをバッファに戻す実装（`this.buffer = chunk + ...`）のため、400 のような
    **成功し得ないエラーが続くとバッファが会議の全文字起こしまで際限なく肥大**する。復旧時には
    蓄積された巨大チャンクが 1 回のリクエストで送られ、入力トークンが跳ね上がる。
    ユーザーには 6 回ごとに開発者向けの生 JSON が表示される（[[termlens-term-extraction]]）

    2026-08-13 に Anthropic のクレジット残高切れで実際に発生した。

> 2026-08-16 解決: 恒久エラー（`APIError` の status が 4xx かつ 408/409/429 以外）で抽出を
> 打ち切り、平易な文言で 1 回だけ通知して再バッファしない実装にした。一時エラーは従来どおり
> 再試行する。あわせてバッファに 2,000 文字の上限を設け、超過時は新しい側を残して切り詰める。
> status が取れない `APIConnectionError` などは**再試行側に倒す**（判別できないものを恒久扱い
> すると、復旧可能な障害で抽出が止まるため）。

    利用者ごとの識別ができないため、1 人に渡したトークンを取り消すには全員分の入れ替えが要る

> 2026-08-16 解決: 「WS 接続の失敗にレート制限がない」を課題から外した。トークンが 128 bit
> あることを確認し、総当たりが成立しないため制限する対象がないと判断した。実装した場合の
> 副作用（ブラウザが 401 と 429 を区別できない、Fly のプロキシで IP を取り違える）とあわせて
> [[termlens-deployment]] に記録した。トークンを弱くする場合はこの判断が崩れる。
13. **Anthropic のクレジット残高を監視していない** — 2026-08-13 に残高切れで用語抽出が全滅した。
    文字起こしは Deepgram なので動き続け、**用語カードだけが出なくなる**ため気付きにくい。
    残高切れは弱点12（バッファ肥大）を誘発する
14. **Fly.io はカード登録が前提** — 未登録だとマシンが 5 分で強制停止される。
    登録済み（2026-08-13）。詳細は [[termlens-deployment]]

> 2026-08-19 追記: **WS 越しの入力は実行時の型を保証しない。** `start` の `shownTerms` を
> 配列チェックだけで通していたため、文字列以外の要素があると `normalizeTerm()` の
> `term.normalize()` で例外になり、**サーバープロセスごと落ちて会議中の全セッションを
> 巻き込んでいた**（実際に再現）。要素の型まで検証すること。あわせて `start`/`stop` の
> Promise に `catch` を付け、1 セッションの失敗がプロセス全体を落とさないようにしている。

> 2026-08-19 追記: **新しいセッションを始める前に内容を必ず空に戻す**（`clearSessionContent()`）。
> `resetSessionState()` はフラグしか戻しておらず、文字起こし・カード・ハイライトは残っていた。
> 従来ホームへ直接戻る経路（トークン誤り・マイク拒否）は「まだカードが1件も無い」時点でしか
> 発生しなかったため表面化しなかったが、復元の失敗はカードが入った状態からホームへ戻る初めての
> 経路で、残骸が次の `start` の `shownTerms` に混ざり、**新しい会議の用語がデデュープで弾かれて
> カード化されない**という形で汚染していた。
